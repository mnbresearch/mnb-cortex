# THE ORDER THESE FILES MUST BE APPLIED IN.
#
# WHY THIS FILE EXISTS.
#
# Until now the apply order was "whatever readdirSync().sort() returns", and
# that is not an order anybody chose — it is an accident of the names. Six
# files could not be applied to an empty database because each referenced
# something a later-sorting file creates:
#
#   2026_default_weekly_brief.sql   needs scheduled_reports  (2026_integrations_layer.sql)
#   2026_integrations_lockdown.sql  needs user_org_rank()    (2026_tenancy.sql)
#   2026_rls_privilege_fix.sql      needs user_org_rank()    (2026_tenancy.sql)
#   2026_msme_43bh.sql              needs cortex_norm_name() (2026_sales_order_customer_link.sql)
#   2026_msme_exposure_fix.sql      needs cortex_norm_name() (2026_sales_order_customer_link.sql)
#   2026_payments_owner_id_nullable.sql — see the note at the end
#
# Production is fine: those dependencies were applied months earlier, by hand,
# in the order they were written. Only a rebuild-from-scratch was broken —
# which is the one scenario where being broken matters, because it is the
# restore path. A backup you can restore needs a schema to restore INTO.
#
# So the order is now declared here rather than inferred, and
# scripts/rehearse-restore.mjs applies exactly this list against a real
# PostgreSQL on every run. Adding a file without listing it fails the
# rehearsal; listing a file that does not exist fails it too. There is one
# order, it is in one place, and it is executed rather than described.
#
# WHY NOT JUST RENAME THE FILES so the sort comes out right? Because sixty-odd
# comments, twenty test scripts and every RUN-*.sql note in this repo refer to
# these files by name, and a rename would silently break that trail while
# looking tidy. The names are history; this file is the order.
#
# Lines starting with # are comments. One filename per line. Applied top to
# bottom, after supabase/schema.sql, supabase/rls.sql and supabase/migration_*.sql.
